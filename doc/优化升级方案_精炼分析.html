三、我自己挖出的优化点（你没想到，但含金量高）

A. 原子库存扣减 / 号源原子占用　P0

这是最容易被忽略、却最能体现工程严谨的点。stock = stock - qty 先查后改在并发下会超卖；号源 used_num++ 会超额挂号。 正确做法：UPDATE medical_drug SET stock=stock-#{qty} WHERE drug_id=#{id} AND stock >= #{qty}，影响行数=0 即库存不足，事务回滚 + 前端提示。号源同理用 WHERE used_num < total_num 原子自增。答辩时这句话能体现你懂并发安全。

B. 业务单据号生成　P0

挂号号、处方号不能随手存。建议 GH + yyyyMMdd + 4位序列 / CF + 日期 + 序列，用数据库当日最大号+1 或 UUID 短码，保证可读且唯一。

C. 关键操作审计日志　P1

开方、发药、退号、改库存是医疗合规核心，应留痕。可建轻量 medical_audit_log（谁/何时/做了什么/对象），不依赖被裁剪的若依 @Log。

D. 修复 doc.html 404　P1

启动类打印 http://localhost:8080/doc.html 但实际没有 Knife4j/Swagger 依赖，打开是 404——答辩演示时很露怯。要么补 Knife4j 依赖让文档真能用，要么把打印去掉/改成正确地址。

E. 输入校验增强　P2

手机号、身份证号目前只在前端掩码，后端缺 Bean Validation 格式校验。加 @Pattern 即可，成本低。

F. 数据级越权防护　P1

若依 RBAC 只到菜单级，A 医生理论上能看 B 医生的患者/处方。毕设可不强求，但应在文档里明确这是已知边界，必要时按 create_by 加数据过滤。

G. 【已知边界声明】RBAC 只到菜单级，数据级越权未做　P2 文档

现状（2026-09-17 核对后的真实情况）：本系统的权限控制由「角色 → 菜单 → 路由」三级构成， 已建 admin / 医生 / 护士 / 药剂师 四类角色并授予 sys_role_menu 菜单权限， 登录鉴权走 Spring Security + JWT（token 存 Redis）。但：

  • 能控制：某个角色能不能看到某个功能菜单（挂号、处方、发药、排班等）。
  • 不能控制：同一菜单内，能看到谁的数据。例如医生角色登录后可查询并编辑全部患者的诊疗记录， 系统不会按 create_by 或主治医生字段做行级过滤。
  • 接口层：既有 Controller 均未加 @PreAuthorize，权限校验仅体现在菜单可见性与登录态上。

为什么这样取舍：毕设体量内，数据级权限需要给每张业务表加归属字段、在查询层统一注入过滤条件， 改动面横跨全部 Mapper 与 Service；收益是「合规完备性」，不是系统能否跑通业务流程。 因此作为明确的已知边界声明，而非隐藏缺陷。

后续补齐路径（两步即可，约 1 小时）：

  1. 业务表补 create_by（已有）/ 主治医生字段，查询 SQL 追加 AND create_by = #{当前用户}；
  2. 接口层加 @PreAuthorize("@ss.hasPermi('medical:diagnosis:list')")， 并注册若依的 ss Bean（PermissionService），使越权访问直接返 403。

答辩话术：可以主动讲——「权限做到菜单级是刻意的范围控制，数据级越权我列为后续迭代项， 并在文档里写清了补齐路径」。主动声明边界，比被问到才承认要好得多。
