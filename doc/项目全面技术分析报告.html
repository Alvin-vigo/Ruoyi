1项目概述

一套基于 RuoYi-Vue 深度裁剪 的轻量级医疗业务管理系统。核心定位是"门诊业务闭环 + 本地 AI 辅助"，覆盖 挂号 → 就诊 → 诊疗 → 开方 → 发药 → 退药 → 随访 全流程，并集成 4 个本地推理的 AI 模块（病历生成、疾病风险预测、胸片初筛、RAG 智能导诊）。 全部组件本地部署，不依赖任何公网服务。

1.1 与标准 RuoYi 的裁剪差异（重要背景）

这不是"装了医疗插件的若依"，而是把若依砍到骨架再长出新业务。已确认的裁剪点：

  • 裁剪无数据权限（DataScope）：BaseEntity 只有 5 个字段（createBy/createTime/updateBy/updateTime/remark），没有原版的 params Map，因此 Mapper XML 中不存在 params.beginTime 写法，时间范围查询改用实体上的显式 beginXxx/endXxx 字段。ruoyi-common/src/main/java/com/ruoyi/common/core/domain/BaseEntity.java
  • 裁剪无 @PreAuthorize / @Log / BusinessType：这些类不存在于 common 模块，业务 Controller 一律不写权限注解，只靠 Security 全局 token 鉴权。
  • 裁剪无动态路由：后端没有 /getRouters 接口，前端菜单是 router/index.js 里的静态常量数组。ruoyi-ui/src/router/index.js
  • 裁剪按钮级权限形同虚设：v-hasPermi 的 hasPermission() 恒返回 true。ruoyi-ui/src/directive/permission.js
  • 裁剪无验证码、无 Swagger/Knife4j：后端没有接口文档依赖，接口文档靠 doc/接口文档.md 手工维护。
  • 新增业务 Controller 不使用 BaseController，而是自写私有 toAjax(int) + PageHelper.startPage() + TableSupport.getDataTable()。

3架构设计

3.1 部署拓扑

浏览器 Vue2 + Element UI :8081 │ │ ① /login /logout /getInfo /medical /monitor /system /tool /gen → 代理到 8080 │ ② /ai-uploads（胸片原图） → 代理到 8000 │ ③ AI 流式 SSE（generateRecordStream） 直连 8000（**绕过后端**） ▼ 后端 Spring Boot 2.7（RuoYi 裁剪） :8080 │ ├─ Spring Security + JWT Filter ──► Redis(Memurai:6379) 仅会话 │ ├─ MyBatis / Druid ─────────────► MySQL(ruoyi_medical:3306) │ └─ AiHttpUtil（RestTemplate，readTimeout 130s） ▼ AI 服务 FastAPI :8000 ├─► Ollama :11434 qwen2.5:7b-instruct-q4_K_M（病历生成 / RAG 生成） ├─► models/model_risk.pkl sklearn 推理（风险预测） ├─► models/chest_cnn.pth PyTorch ResNet18（胸片三分类） └─► data/chroma_db + 本地 embedding Chroma 检索（RAG）

三条链路的取舍：普通请求走"前端→后端→AI"的代理链（便于鉴权与落库）；胸片原图直连 AI 的静态目录（避免后端做文件流中转）；AI 流式 SSE 前端直连 FastAPI（避免后端实现 SSE 转发）。代价是 ③ 这条链完全不带 token，靠 FastAPI 全开 CORS 兜底。

5核心业务流程与数据流

5.1 门诊主闭环（本项目的骨架）

① 挂号 POST /medical/registration ├─ 生成单号 GH+yyyyMMdd+4位随机 ├─ UPDATE medical_schedule SET used_num=used_num+1 WHERE ... AND used_num<total_num ← 原子占号 │ 返回 0 行 → ServiceException("号源已满，无法挂号") └─ medical_registration.reg_status = '0'（待就诊） ② 开始就诊 POST /medical/registration/start-visit/{id} ├─ 前置校验：reg_status 必须为 '0'；patientId / dept / doctorName 非空 ├─ INSERT medical_diagnosis（草稿：status='1'，diagnosis_result='待完善'，registration_id 关联） └─ medical_registration.reg_status: 0 → 1（已就诊） ③ 诊疗记录 /medical/diagnosis/**（CRUD + 费用汇总 fee-summary） └─ 可从患者页一键触发 AI 病历生成回填（diagnosis/index.vue 的 handleAiGenerate） ④ 开方 POST /medical/prescription ├─ 单号 CF+yyyyMMdd+4位随机，status='0'（待发药） ├─ 按患者补全 patient_name / patient_allergy ├─ 按价目表自动计价：selectPriceByDrugName(drugName) 覆盖单价，total = Σ qty×price ├─ 过敏校验：AllergyChecker.check(过敏史, 药品名) → allergy_warning └─ INSERT medical_prescription + N 条 medical_prescription_item ⑤ 发药 POST /medical/prescription/dispense ├─ 5 秒防重复锁（ConcurrentHashMap，内存级） ├─ 逐条校验：发药量 ≤ 未发量 → 效期未过 → UPDATE medical_drug SET stock=stock-#{qty} │ WHERE drug_id=#{id} AND stock>=#{qty} ← 原子扣库存，0 行即"库存不足" ├─ UPDATE medical_prescription_item SET dispensed_quantity=... ├─ INSERT medical_dispensing（发药流水，status='0'） └─ 重算处方状态：全发完='2' / 部分='1' / 未发='0' ⑥ 退药 POST /medical/prescription/return/{id} ├─ 只处理 status in (null,'0') 的发药记录（幂等） ├─ UPDATE medical_drug SET stock=stock+#{qty}（回滚） ├─ 发药记录 status → '1'（已退），dispensed_quantity 回退 └─ 处方状态恢复 '0' 旁路：退号 POST /medical/registration/refund/{id} → reg_status='2' + used_num-1 释放号源 作废 POST /medical/prescription/cancel/{id} → prescription_status='3' 审计：开方 / 发药 / 退药 / 退号 四处写 medical_audit_log（try-catch 吞异常，不影响主流程）

6.4 前端请求解包约定（最容易踩坑的一处）

ruoyi-ui/src/utils/request.js 的响应拦截器返回的是 res.data（整个 AjaxResult 体），不是 res.data.data。因此：

  • 列表接口 → 用 res.rows / res.total（TableDataInfo 顶层字段）
  • 单对象接口 → 用 res.data（AjaxResult 的 data 字段）

10关键实现细节

10.1 并发安全的两条原子 SQL（项目的核心正确性保障）

-- ruoyi-system/src/main/resources/mapper/MedicalDrugMapper.xml（库存扣减，0 行 = 库存不足）
UPDATE medical_drug SET stock = stock - #{quantity}
 WHERE drug_id = #{drugId} AND stock >= #{quantity}

-- MedicalScheduleMapper.xml（号源占用，0 行 = 号源已满）
UPDATE medical_schedule SET used_num = used_num + 1
 WHERE schedule_id = #{scheduleId} AND used_num < total_num

-- 对称的回退语句
UPDATE medical_drug     SET stock    = stock    + #{quantity} WHERE drug_id     = #{drugId}
UPDATE medical_schedule SET used_num = used_num - 1
 WHERE schedule_id = #{scheduleId} AND used_num > 0

-- MedicalMessageMapper.xml（已读标记，条件带 read_status='0'，天然幂等）
UPDATE medical_message SET read_status = '1'
 WHERE receiver = #{receiver} AND read_status = '0'

把"判断 + 扣减"压进一条 SQL 的 WHERE 条件里，用影响行数代替"先 SELECT 再 UPDATE"，是本并发量级下最经济的做法。Service 侧只需判断 rows == 0 抛 ServiceException。

10.2 幂等与防重设计

  • 发药 5 秒防重：MedicalPrescriptionServiceImpl 里 ConcurrentHashMap<String, Long> dispensingLocks，同一处方 5 秒内二次发药抛"操作过于频繁"。
  • 退药幂等：只处理 status == null || "0" 的发药记录，已退的不会被二次回滚。
  • 知识库同步幂等：只查 synced = '0' or synced is null，同步后 markSynced；且 insert/update 时强制 setSynced("0")，正文变更必然重新入库。
  • 站内信去重：existsUnreadByTypeAndRelated(type, relatedId, receiver) 命中则不重复推送。
  • 身份证唯一校验：SQL 里带 and id_card != '' 与 patient_id != #{patientId}，且 Service 中空证件号直接返回 "0"（允许无证件患者）。

10.3 审计的"不阻塞主流程"设计

MedicalRegistrationServiceImpl / MedicalPrescriptionServiceImpl 中的私有 audit(...) 方法整体包在 try-catch 里吞掉异常；操作人从 SecurityContextHolder 取，取不到回落 "system"。即审计写失败不会让挂号/发药回滚——这是有意的取舍。

11潜在问题与改进点

P0 · 会直接导致功能失败

P0-1401 处理抛 ReferenceError，登录失效后无法跳转

ruoyi-ui/src/utils/request.js 第 3 行只 import { getToken }，但第 37 行调用了 removeToken()——未导入。token 过期时会先弹错误提示，然后抛 ReferenceError: removeToken is not defined，后续的 location.href='/login' 与 Promise.reject 都不会执行，用户会卡在"点了没反应"的状态。

// request.js:3
import { getToken } from '@/utils/auth'      // ← 只有 getToken
// request.js:35-42
} else if (code === 401) {
  Message.error('认证失败，请重新登录')
  removeToken()                              // ← 未定义！
  if (location.href.indexOf('/login') === -1) { location.href = '/login' }
  return Promise.reject('认证失败')
}

修法：把第 3 行改成 import { getToken, removeToken } from '@/utils/auth'。src/utils/auth.js 确实导出了 removeToken。

P0-2五个导出功能的 URL 缺前导斜杠

导出写成相对路径，与 proxy 规则 /medical 不匹配：

// patient/index.vue:440      this.download('medical/patient/export',   {...})
// diagnosis/index.vue:399    this.download('medical/diagnosis/export', {...})
// feeReport/index.vue:173    this.download('medical/diagnosis/export', {...})
// drug/index.vue:487         this.download('medical/drug/export',      {...})
// followup/index.vue:351     this.download('medical/followup/export',  {...})

而 monitor/job/index.vue:334 写的是 '/monitor/job/export'（带斜杠，正确）。dev 环境下相对 URL 会拼成 http://localhost:8081/medical/...，被 devServer 的 history fallback 吃掉返回 index.html，导出静默失败。修法：五处补前导 /。

P0-3@Validated @RequestBody 的校验错误被吞成"系统繁忙"

ruoyi-framework/.../web/exception/GlobalExceptionHandler.java 处理了 ServiceException、BindException、RuntimeException、Exception，但没有 MethodArgumentNotValidException。而 @Validated @RequestBody 触发的正是它（患者身份证/手机号 @Pattern 走的这条路），会落到最外层 Exception 分支返回"系统繁忙，请稍后重试"，前端拿不到具体哪个字段不合法。

P0-4数据库密码明文入库

application.yml:19 password: "<已脱敏>" 曾以明文写在配置里，未进入 Git 历史（已用 git log -S 核实）。改进：改用环境变量 ${DB_PASSWORD} 或外部配置；若仓库要公开，至少 rotation 一次密码。同类问题：Redis 无密码（password: 留空），FastAPI 与后端 CORS 均 allow_origins=* + allow_credentials=true（演示可接受，生产需收紧）。

P1 · 正确性风险与一致性债务

P1-1低库存阈值三处口径不一致

位置阈值

P1-2统计缓存用 JVM 静态 Map，且 dashboard 与 README 口径不符

MedicalStatisticsServiceImpl 用 static Map cache + static AtomicLong cacheTs，TTL 1 小时。问题：多实例部署时各实例缓存不一致；类卸载/热部署会丢；且缓存不是 Redis，与项目"Redis 只存 token"的现状一致但没在文档里说明。

P1-3/medical/audit/count 全表查询

MedicalAuditLogController.java 的 /count 实现是 selectMedicalAuditLogList(new MedicalAuditLog()).size()——先全表捞出 List 再取 size，没有分页也没有 count(*)。审计表是增长最快的表之一，数据量大后会拖垮内存。修法：加 selectCount(...) 走 COUNT(1)。

P1-4诊疗主键用 max(id)+1，非原子

MedicalDiagnosisServiceImpl.insertMedicalDiagnosis：if (diagnosisId == null) setDiagnosisId(selectNextDiagnosisId())，而 selectNextDiagnosisId() 是 select ifnull(max(diagnosis_id),0)+1。并发插入两条会得到相同 ID。修法：改成表自增 + useGeneratedKeys。

P1-5发药防重锁是单机内存锁

ConcurrentHashMap dispensingLocks 只在单 JVM 内有效，多实例部署失效；且 Map 只增不删（键是处方号），长时间运行会缓慢增长。建议：改用 Redis SET NX EX 5，或给 Map 加定期清理。
