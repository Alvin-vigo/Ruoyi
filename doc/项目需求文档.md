## 2. 项目概述

### 2.1 项目背景及业务目标
面向中小型医疗机构，构建一套覆盖“患者就诊—医生诊疗—药房发药—随访管理”全流程的轻量级医疗业务管理系统，并集成 AI 辅助能力（智能病历、风险预测、胸片初筛、智能导诊），提升门诊作业效率与决策辅助水平。

**业务目标（可度量）**
1. 实现挂号 → 诊疗 → 开方 → 发药 → 随访的**业务闭环**，关键操作（开方 / 发药 / 退药 / 退号）全程留痕。
2. 药品库存与效期**自动校验**，杜绝过期药发出、超量发药。
3. 提供 4 项核心运营指标看板（挂号量 / 处方量 / 发药总量 / 库存预警）。
4. 集成 4 项 AI 能力，其中病历生成、风险预测、胸片识别为本地模型推理，导诊为本地知识库检索增强，全程**不依赖外部公网服务**。

### 2.2 用户角色与特点
| 角色 | 说明 | 使用场景 |
|------|------|----------|
| 管理员（admin） | 系统内置超级管理员 | 全部菜单与数据；演示默认账号 `admin / admin123` |
| 门诊医生 | 挂号、诊疗、开方 | 诊疗记录、处方发药 |
| 药房人员 | 发药、退药、药品维护 | 药品管理、处方发药 |
| 导诊 / 护士 | 患者建档、随访、站内信 | 患者管理、随访、消息 |

> 当前裁剪版 RBAC 仅到**菜单级**（角色→菜单权限），未做按钮级 / 数据级权限隔离；多角色差异通过菜单可见性体现，详见第 6、8 节。

### 2.3 运行环境
**硬件环境**
- 服务器端：x86_64，≥ 8 GB 内存；AI 胸片推理建议具备 NVIDIA GPU（本项目实测 RTX 4050 6GB，CUDA 可用）。
- 客户端：常规办公 PC 或移动端浏览器。

**软件环境**

## 3. 功能需求

> 每个模块按 **功能描述 / 输入 / 输出 / 处理规则与边界 / 异常消息** 描述。
> 通用约定：所有业务接口需在请求头携带 `Authorization: Bearer <token>`；统一响应体为 `{ code, msg, data }`，`code=200` 为成功。

### 3.1 认证与登录
- **功能描述**：用户输入账号、密码登录系统，获取 JWT；登录后可访问受保护资源；退出清除令牌。
- **输入**：`{ username, password }`。
- **输出**：`{ token, ... }`；`GET /getInfo` 返回用户、角色、权限。
- **处理规则与边界**：
  - 默认演示账号 `admin / admin123`。
  - **当前未启用图形验证码**（明确边界，见第 8 节）。
  - 令牌存于 Redis（`login_tokens:xxx`），后端重启前需确保 Redis（Memurai）已启动。
- **异常消息**：账号或密码错误返回 401；token 失效返回 401 并提示重新登录。

### 3.2 患者管理
- **功能描述**：维护患者档案（姓名、性别、身份证号、手机号、过敏史等）。
- **输入**：患者表单字段。
- **输出**：患者列表 / 详情。
- **处理规则与边界**：
  - 身份证号（18 位，MOD 11-2 校验）、手机号（`1[3-9]` 开头 11 位）后端 `@Pattern` 校验，前端同规则。
  - 演示示例（已校验合法）：`110101199001010015` / `13812345678`。
- **异常消息**：身份证格式不正确；手机号格式不正确。

### 3.3 挂号管理
- **功能描述**：患者挂号，生成挂号单并占用对应排班号源；支持退号、开始就诊。
- **输入**：`patientId`、`scheduleId`（排班 / 号源）。
- **输出**：
  - `POST /medical/registration` → 单号 `GH + yyyyMMdd + 4位随机`，号源 `used_num +1`（不超过 `total_num`）。
  - `POST /medical/registration/refund/{id}` → 退号，释放号源。
  - `POST /medical/registration/start-visit/{id}` → 建诊疗草稿（关联 `registration_id`）、挂号状态转“已就诊”。
- **处理规则与边界**：
  - 号源占用为原子操作：`UPDATE ... SET used_num=used_num+1 WHERE ... AND used_num<total_num`，影响行数 0 视为号源已满。
  - “开始就诊”仅可触发一次（按钮置灰防重复）。
- **异常消息**：号源已满；挂号记录不存在。

### 3.4 诊疗管理
- **功能描述**：记录主诉、诊断结果、医嘱；支持 AI 辅助写病历。
- **输入**：诊疗表单（患者 ID、就诊日期、科室、医生、主诉、诊断、方案、费用、状态）。
- **输出**：诊疗列表 / 详情；AI 生成的病历草稿。
- **处理规则与边界**：
  - **诊疗 ID 删除后复用**：新增时取 `MAX(diagnosis_id)+1` 显式赋值（MySQL 自增不回收，已定制）。
  - AI 辅助写病历：按患者 ID 自动查询档案（姓名 / 年龄 / 性别 / 过敏史）填充；Ollama 不可用则降级为模板草稿（约 40–52 秒实时推理，或秒级降级）。
- **异常消息**：患者 ID 不存在时提示“患者 ID x 不存在”（不再要求手填姓名）。

### 3.5 药品管理
- **功能描述**：维护药品目录、库存；展示近效期预警。
- **输入**：药品表单（名称、规格、库存、有效期等）。
- **输出**：药品列表；近效期列表（剩余天数）。
- **处理规则与边界**：
  - 近效期预警阈值：距有效期 ≤ 90 天高亮。
  - 剩余天数显示规则：未过期显示“N 天”；已过期显示红色“**-N 天（已过期）**”（已修复 NaN）。
  - 种子数据仅“板蓝根颗粒”故意设为过期，用于演示拦截。
- **异常消息**：无（基础 CRUD）。

### 3.6 处方与发药（业务闭环核心）
- **功能描述**：医生开方，系统按价目表自动计价并做过敏校验；药房发药做效期 / 库存校验并扣减库存；支持退药回滚。
- **输入**：
  - `POST /medical/prescription`：`patientId`、药品明细（含数量）。
  - `POST /medical/dispensing/dispense`：处方 ID、发药人。
  - `POST /medical/dispensing/return/{id}`：退药（幂等）。
- **输出**：
  - 处方生成 `CF` 前缀单号，状态“待发药”，返回总价。
  - 发药成功状态“已发药”，库存扣减。
  - 退药库存回滚。
- **处理规则与边界**：
  - **自动计价**：依据 `price_item` 价目表。
  - **过敏校验**：患者过敏史与处方药品冲突则拦截。
  - **发药效期校验**：过期药品禁止发出。
  - **库存扣减为原子操作**：`UPDATE medical_drug SET stock=stock-#{qty} WHERE drug_id=#{id} AND stock>=#{qty}`，影响行数 0 = 库存不足。
  - **退药幂等**：同一发药记录重复退药仅回滚一次。
  - 开方 / 发药 / 退药 / 退号四类操作均落 `medical_audit_log`（失败不影响主流程）。
- **异常消息**：库存不足；药品已过期；存在过敏冲突；处方不存在。

### 3.7 随访管理
- **功能描述**：制定随访计划、记录随访结果。
- **输入 / 输出**：随访表单与列表。
- **处理规则与边界**：关联患者与诊疗记录；基础 CRUD。

### 3.8 站内信
- **功能描述**：向用户发送站内消息，统计未读数。
- **输入**：`receiver`（登录用户名，非姓名）、标题、内容。
- **输出**：消息列表、未读总数。
- **处理规则与边界**：未读数接口返回数字本身（`data`），前端直接展示，不解析响应体。
- **异常消息**：接收人不存在。

### 3.9 价目管理
- **功能描述**：维护诊疗项目价目表，供处方自动计价引用。
- **输入 / 输出**：价目项目 CRUD。
- **处理规则与边界**：处方计价以价目表为准，缺失项目需先维护。

### 3.10 排班管理
- **功能描述**：维护医生出诊排班与号源；供挂号选择。
- **输入**：排班日期、科室、医生、时段（上午 / 下午）、号源总数。
- **输出**：排班列表；号源下拉（供挂号页）。
- **处理规则与边界**：
  - 日期统一格式化为 `yyyy-MM-dd`，不展示 UTC 原始串。
  - 过期排班状态显示“已过诊”，修改时禁止选过去日期，挂号页过滤过期号源。
- **异常消息**：排班不存在；号源不足。

### 3.11 审计日志
- **功能描述**：查询关键操作留痕（开方 / 发药 / 退药 / 退号）。
- **输入 / 输出**：按操作类型、时间区间检索。
- **处理规则与边界**：只读，由业务动作自动写入，不可修改。

### 3.12 统计看板
- **功能描述**：聚合 4 项运营指标。
- **输出**：挂号量、处方量、发药总量、库存预警数。
- **处理规则与边界**：实时聚合，演示环境基于种子数据。

### 3.13 定时任务（Quartz）
- **功能描述**：可视化调度后台任务（如随访提醒、统计快照）。
- **输入 / 输出**：任务 CRUD、立即执行、暂停 / 恢复。
- **处理规则与边界**：业务任务 `job_id` 从 100 起（1/2/3 已被系统占用）。

### 3.14 AI 智能模块
后端（8080）→ FastAPI（8000）→ Ollama（11434）/ 本地模型 / Chroma 向量库；Java 侧 `AiHttpUtil` + `MedicalAiController`（约 18 端点），前端 `views/medical/ai/` 5 页。

#### 3.14.1 病历生成
- **输入**：患者 ID（自动带出档案）。
- **输出**：结构化病历草稿（主诉 / 现病史 / 初步诊断 / 医嘱）。
- **规则**：Ollama 实时生成（约 40–52 秒）；Ollama 不可用降级模板。

#### 3.14.2 风险预测
- **输入**：8 项临床特征（怀孕次数、血糖、血压、皮褶厚度、胰岛素、BMI、糖尿病家族史、年龄）。
- **输出**：风险等级 + 概率 + 特征贡献。
- **规则**：`models/model_risk.pkl`（AUC≈0.813）；特征顺序以 `models/risk_features.json` 为真相源。

#### 3.14.3 胸片识别（三分类）
- **输入**：胸片图片。
- **输出**：`{ result, confidence, probs(三类), classes }`，并落库 `medical_chest_xray.probs_json`。
- **规则**：`models/chest_cnn.pth`（val_acc≈0.962）；类别 `COVID-19 / NORMAL / Viral Pneumonia`；推理与训练使用一致 ImageNet 归一化。

#### 3.14.4 智能导诊（RAG）
- **输入**：自然语言问询（如“胸口压榨样疼伴出汗挂什么科”）。
- **输出**：分诊建议 + 引用知识库条目。
- **规则**：本地 `paraphrase-multilingual-MiniLM-L12-v2` 嵌入 + Chroma 检索；相似度阈值 0.55 过滤，过滤后仍无匹配则拒答（防幻觉）；知识库 `medical_rag_knowledge` 18 条已与向量库同步。

## 4. 非功能需求

### 4.1 性能
- 常规页面响应 ≤ 3 秒；含 AI 推理的页面（病历生成）允许 40–60 秒并给出进度提示。
- 关键写操作（扣库存、占号源）为数据库原子更新，避免并发超卖。

### 4.2 安全
- JWT 无状态鉴权 + Redis 令牌存储；密码不落响应。
- 身份证 / 手机号格式服务端校验，防脏数据。
- 过敏冲突、过期药、超量发药在服务端强制拦截。

### 4.3 兼容性
- 前端适配 Chrome / Edge / Firefox 主流浏览器；响应式布局兼容桌面与移动端。

### 4.4 可维护性与可观测性
- 统一响应体、统一异常处理（`ServiceException` 透传 message）。
- 关键操作审计留痕。
- 后端日志、AI 服务日志、前端 dev 日志分离，便于排障。

### 4.5 数据
- MySQL 8.0，字符集 `utf8mb4`；导入 SQL 须带 `--default-character-set=utf8mb4`。
- 业务闭环表与审计表外键语义由应用层保证。

## 5. 接口与输入输出约定

### 5.1 API 风格
- RESTful，前缀按模块划分：`/medical/*`（业务）、`/monitor/*`（任务）、`/medical/ai/*`（AI）。
- 列表接口支持 `pageNum / pageSize` 分页。

### 5.2 统一响应
```json
{ "code": 200, "msg": "操作成功", "data": { } }
```
- `code=200` 成功；非 200 为业务 / 校验失败，`msg` 为可读原因。

### 5.3 鉴权
- 登录拿 token → 后续请求头 `Authorization: Bearer <token>`。
- 前端 dev 代理（`vue.config.js`）已补齐 `/login`、`/getInfo`、`/logout` 转发。

## 6. 约束条件

1. **技术栈约束**：后端 Spring Boot（若依裁剪版）、前端 Vue2 + Element UI、AI 服务 FastAPI + PyTorch + Chroma；不得引入与生产环境不兼容的依赖。
2. **运行环境约束**：启动顺序 Memurai(6379) → MySQL(3306) → 后端(8080) → AI(8000) → Ollama(11434) → 前端(8081)；后端须以 `--server.port=8080` 显式启动（避免环境变量注入随机端口）。
3. **合规约束**：患者个人信息仅用于演示，禁止入库真实身份；AI 结果为辅助参考，不替代医生诊断。
4. **资源约束**：胸片训练需 GPU venv（`chest-train`）；病历生成依赖本地 Ollama 模型，未预拉取时需先 `ollama pull`。
5. **裁剪边界**：不实现原若依的验证码、代码生成器、审计登录日志等未裁剪模块。

## 7. 验收标准（可测试）

| 编号 | 验收项 | 通过标准 |

## 8. 已知限制与边界（明确边界）

1. **RBAC 仅到菜单级**：角色差异通过菜单可见性体现，未做按钮级 / 数据级权限隔离（演示与答辩已知边界）。
