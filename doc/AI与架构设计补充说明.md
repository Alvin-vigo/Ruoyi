## 一、M08#3 智能病历"采纳"与主流程联动

**现状（V1.0）**：AI 生成病历草稿后，医生在 AI 病历页点击"采纳"，仅将状态置为已采纳并保存为一条 `medical_ai_record`。

**说明**：V1.0 暂不自动写回 `medical_diagnosis`（诊疗记录），原因有二——
1. AI 输出为自然语言草稿，直接写回结构化字段（现病史/初步诊断）需做字段抽取，V1.0 不做；
2. 医疗数据以"经治医生最终确认"为准，草稿必须经过人工复核。

**后续版本（V2.0）**：在接诊页（`diagnosis/index.vue`）已埋好联动入口——点击"AI 生成病历"按钮，调用 `generateRecord` 后将返回的 `现病史 / 初步诊断` 一键回填到当前接诊表单的 `presentIllness / diagnosisResult` 字段（代码已实现回填逻辑，V1.0 仍由医生点"保存"确认）。**所有 AI 生成内容必须经医生确认后方可进入正式诊疗记录**，这是系统的硬性约束。

## 三、文档#6 药品库存出入库流水

**现状（V1.0）**：`medical_drug.stock` 为直接维护模式——药师在药品管理页手动修改库存数值（入库 / 出库 / 盘点调整均直接改 `stock` 字段），**暂未做入库单、出库单与库存流水表**。

**说明**：V1.0 聚焦核心业务闭环演示，库存以"当前值"为准即可满足发药场景；不做流水是为了控制数据模型复杂度。

**后续版本（V2.0）**：新增 `medical_drug_stock_log`（入库/出库/盘点/报损，含单据号、数量、操作人、时间）+ `medical_drug_inbound` / `medical_drug_outbound` 单据表，任何库存变动先落单据再更新 `stock`，实现可追溯。

## 四、文档#8 AI 微服务接口鉴权

**现状**：`ruoyi-ai`（FastAPI，端口 8000）当前**无 Token 鉴权**。

**V1.0 防护**：服务**仅绑定 `127.0.0.1` 回环地址**（`main.py` 启动 `host="127.0.0.1"`），不对外暴露；后端 `AiHttpUtil` 通过本机 `http://127.0.0.1:8000` 调用，外部网络无法直连。

**生产化要求（上线前必做）**：
1. 增加 API Token 校验中间件（请求头 `X-API-Token` 或 Bearer）；
2. 令牌由后端配置下发，不硬编码；
3. 如需跨机部署，必须上 HTTPS + 网关鉴权，禁止裸端口公网暴露。

## 五、优化#3 架构选型论证

### 5.1 为什么用「单体 + 内置 AI 微服务」而不是纯微服务

| 维度 | 本方案（单体 RuoYi + 旁路 AI 服务） | 纯微服务（Spring Cloud） |
|------|--------------------------------------|--------------------------|
| 部署复杂度 | 1 个后端 jar + 1 个 AI 进程，Nginx 反代 | 注册中心 + 网关 + 多个服务，运维重 |
| 学习/改造成本 | 复用 RuoYi 成熟脚手架，本科毕设周期可控 | 需自搭全套微服务基建 |
| 模块耦合 | 业务耦合但毕设范围小，可接受 | 解耦彻底但过度设计 |
| 结论 | **毕设场景最优**：业务规模小、追求可演示、可答辩 | 适合中大型生产系统 |

> 关键取舍：AI 能力（Ollama / sklearn / Chroma）与 Java 技术栈差异大，强行塞进单体反而臃肿，故将 AI 拆为**独立的 FastAPI 旁路服务**，通过 HTTP 调用。这是"该分的分、不该分的合"的务实选择。

### 5.2 为什么用「单节点 + 单库」而不是集群

| 维度 | 单节点 MySQL + 单应用 | 主从 / 集群（MySQL Group Replication） |
|------|------------------------|----------------------------------------|
| 数据量 | 演示数据 < 万级，单库轻松承载 | 千万级才显价值 |
| 可用性要求 | 毕设演示，停机可接受 | 7×24 高可用才需要 |
| 成本 | 零额外资源 | 多节点机器 + 运维 |
| 结论 | **演示场景足够**，集群属过度工程 |

### 5.3 为什么用「MySQL 全文索引」而不是 Elasticsearch

| 维度 | MySQL `LIKE` / 全文索引 | Elasticsearch |
|------|--------------------------|---------------|
| 导诊知识库规模 | 数十条 ~ 数百条，MySQL 足矣 | 百万级文档才需 ES |
| 检索精度 | `MATCH ... AGAINST` 或语义向量（Chroma 旁路）满足 | 中文分词更强但引入重组件 |
| 运维 | 零额外组件 | 需独立集群 + 同步管道 |
| 结论 | **轻量优先**；语义检索已由 `ruoyi-ai` 的 Chroma 向量库承担，RuoYi 侧无需再引 ES |

> 一句话总结：**所有选型都遵循"场景驱动、能用最小代价满足需求、不为演示而堆架构"的原则**，这正是本科毕业设计应展示的工程判断力。
