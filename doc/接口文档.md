# 若依医疗管理系统接口文档

## 概述

本文档描述若依医疗管理系统后端提供的 RESTful API 接口，涵盖患者管理和诊疗信息两大模块。

**基础路径**: `http://localhost:8080`

**通用响应格式**:
```json
{
  "code": 200,
  "msg": "操作成功",
  "data": {}
}
```

**分页响应格式**:
```json
{
  "code": 200,
  "msg": "查询成功",
  "total": 100,
  "rows": []
}
```

---

## 一、患者管理接口

### 1.1 查询患者列表

- **URL**: `/medical/patient/list`
- **Method**: `GET`
- **描述**: 分页查询患者信息列表

**请求参数**:

| 参数名 | 类型 | 必填 | 说明 |
|--------|------|------|------|
| pageNum | Integer | 否 | 当前页码，默认1 |
| pageSize | Integer | 否 | 每页条数，默认10 |
| patientName | String | 否 | 患者姓名（模糊查询） |
| gender | String | 否 | 性别（0男 1女 2未知） |
| phone | String | 否 | 联系电话（模糊查询） |
| idCard | String | 否 | 身份证号 |
| status | String | 否 | 状态（0正常 1住院 2出院 3死亡） |

**响应示例**:
```json
{
  "code": 200,
  "msg": "查询成功",
  "total": 5,
  "rows": [
    {
      "patientId": 1,
      "patientName": "张三",
      "gender": "0",
      "birthDate": "1990-05-15",
      "idCard": "110101199005151234",
      "phone": "13800138001",
      "address": "北京市朝阳区建国路88号",
      "bloodType": "A",
      "allergyHistory": "青霉素过敏",
      "status": "0",
      "createTime": "2024-01-15 09:30:00"
    }
  ]
}
```

## 八、诊疗费用明细报表接口

> 说明：诊疗明细的 **Excel 导出** 已内置于第二章诊疗模块（`GET /medical/diagnosis/export`，见 2.6）。本章仅补充新增的**费用汇总统计接口**及独立报表页所需的数据接口。前端对应页面为 `medical/feeReport/index`，支持按患者/科室/状态/日期范围筛选，并展示「总金额 / 记录数 / 均值」三张汇总卡片。

### 8.1 诊疗费用汇总统计

- **URL**: `/medical/diagnosis/fee-summary`
- **Method**: `GET`
- **描述**: 在诊疗列表筛选条件基础上，统计诊疗费用的记录数、总金额、平均值。用于费用明细报表页顶部汇总卡片，亦支持单独调用。

**请求参数**（与 2.1 一致）:

| 参数名 | 类型 | 必填 | 说明 |
|--------|------|------|------|
| patientId | Long | 否 | 患者ID |
| patientName | String | 否 | 患者姓名（模糊查询） |
| department | String | 否 | 就诊科室 |
| doctorName | String | 否 | 主治医生（模糊查询） |
| status | String | 否 | 状态（0待就诊 1就诊中 2已完成） |
| beginVisitDate | String | 否 | 就诊开始日期 |
| endVisitDate | String | 否 | 就诊结束日期 |

**响应示例**:

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": {
    "totalCount": 12,
    "totalCost": 1860.00,
    "avgCost": 155.00
  }
}
```

> 字段说明：`totalCount`=符合条件的诊疗记录数；`totalCost`=费用合计（无数据时返回 0）；`avgCost`=单条均值（无数据时返回 0）。汇总与明细共用同一套筛选条件，保证卡片数字与下方明细表完全一致。

## 十二、定时任务业务集成示例（随访逾期 / 低库存预警）

> 两个示例任务已在 `quartz.sql` 中以 `sys_job` 记录形式种入，应用启动时由 `SysJobServiceImpl.init()` 自动加载并注册到调度器（复用第十章的 Quartz 框架）。任务执行后通过 `SpringUtils` 取业务服务，将提醒写入站内信（`medical_message` 表，type=1 低库存 / type=2 随访逾期）。

| 任务名 | 调用目标（invokeTarget） | Cron | 行为 |
|--------|--------------------------|------|------|
| 随访逾期提醒任务 | `followupRemindTask.scanOverdueFollowup` | `0 0 8 * * ?`（每天08:00） | 扫描 `status=0` 且 `next_followup_date < 今天` 的随访，向随访人推送站内信；同一随访已存在未读提醒则跳过 |
| 药品低库存预警任务 | `medicalRemindTask.scanLowStock('10')` | `0 0 9 * * ?`（每天09:00） | 扫描库存≤阈值的药品，向 admin 推送站内信；同一药品已存在未读预警则跳过 |

**任务类位置**：`ruoyi-quartz/src/main/java/com/ruoyi/quartz/task/FollowupRemindTask.java`、`MedicalRemindTask.java`。去重逻辑由 `IMedicalMessageService.existsUnreadByTypeAndRelated` 提供，避免每日重复推送。
